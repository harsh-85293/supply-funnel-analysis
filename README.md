# Captain Acquisition take-home

## The three deliverables

| Brief asks for | File | Limit | Actual |
|---|---|---|---|
| A memo, max 2 pages | **`deliverables/MEMO.pdf`** (source: `MEMO.md`) | 2 pages | 2 pages |
| Your working, runs end to end from the raw CSVs | **`run_all.py`** + `src/` + this README | — | ~90 seconds |
| A deck, max 6 slides | **`deliverables/DECK.pdf`** and **`DECK.pptx`** (source: `DECK.md`) | 6 slides | 6 slides |

`deliverables/SPEAKER_NOTES.md` holds the 10-minute timing plan, the three
interruptions I've prepared for, and the questions I expect in the 20-minute Q&A.
It is deliberately outside the deck so the deck stays at six slides.

## Run it

Requires Python 3.10+. From the repository root:

```bash
python -m venv .venv
.venv/Scripts/activate          # Windows;  source .venv/bin/activate on macOS/Linux
pip install -r requirements.txt

python run_all.py               # analysis + chart exhibits  -> outputs/
python build_pdfs.py            # MEMO.pdf and DECK.pdf
python build_pptx.py            # DECK.pptx (native PowerPoint of the deck)
python verify_claims.py         # checks the deliverables against the analysis
```

With [uv](https://docs.astral.sh/uv/) the setup is one line:

```bash
uv venv --python 3.12 .venv && uv pip install --python .venv -r requirements.txt
```

No arguments, no configuration, no network access. Deterministic — the only
randomness is a seeded parametric bootstrap behind the campaign's confidence
interval.

`build_pdfs.py` renders the markdown and then **asserts** the page and slide
counts, so the brief's limits are verified rather than eyeballed. It exits
non-zero if either is exceeded.

`verify_claims.py` runs 166 checks: every figure quoted in the memo and deck
against `outputs/`, several recomputed straight from the raw CSVs rather than
trusting the pipeline, plus the brief's format rules (page count, slide count,
and no code or raw field names in the rendered text). It caught five genuine
discrepancies while I was writing the memo.

`src/config.py` is the place to look first. Every judgement call — the cohort
cutoff, document requirements by vehicle type, which failure reasons count as a
photo problem, the night window, the assumed driving speed — is declared there
rather than buried in the analysis.

## The four decisions that drive the results

**1. Cohort: signups 1 Jan – 15 Jun 2026, n = 22,561.**
The extract is 30 June 23:59. The longest signup-to-decision latency observed is
14.1 days, so a signup needs ~15 days before its outcome is final. 1,297 captains
are still `in_progress`, all of them June signups. Pooling all 25,000 reports A2O
as 16.82% instead of 17.59% — a 0.77 pp error that is pure censoring. One
unresolved captain remains in the cohort and is kept in the denominator as
not-approved.

**2. Every funnel measure is rebuilt from `doc_events`, not from `approvals.csv`.**
`docs_cleared` disagrees with the event log for 451 captains (1.80%), always in
the same direction — it overstates progress by 1 to 6 documents. The binary
"cleared everything" gate *is* consistent across both sources, which is why
totals tie. `last_stage_reached` turns out to be forward-looking (the stage the
captain was stuck on, i.e. the first uncleared document) rather than the last
document they touched; both readings are reconstructed independently in
`dataload.py`.

**3. Document requirements are vehicle-aware.**
Permit applies to Auto and Cab only, so E-Rickshaw captains require 5 documents.
Confirmed in the data: zero Permit events for E-Rickshaw, and approved E-Rickshaw
captains top out at 5 cleared documents. Defining the funnel as "cleared 6
documents" would label all 4,756 E-Rickshaw signups as failures.

**4. Stage conversion is conditioned on reaching the stage.**
A captain "reaches" document *k* only after clearing every required document
before it. Each stage's loss splits into *reached it and never submitted*
(a motivation problem) and *submitted and never passed* (a capture or eligibility
problem), because those have different owners and different fixes.

## On the CAMP_WA_002 method

The campaign has a trigger documented nowhere in the brief: it is sent only after
a captain clears their second document, a median of 6.7 hours later. Zero of 7,981
recipients received it before that point. `campaign.py` recovers this from the
data, then walks the estimate down in four steps
(`outputs/a3_estimate_ladder.csv`):

| | Lift |
|---|---|
| Naive, recipients vs all others | +17.93 pp |
| Restricted to captains who cleared 2+ documents | +4.16 pp |
| Also requiring both arms active at the send point | +3.70 pp |
| Plus covariate adjustment (logit average marginal effect) | +3.82 pp [+2.31, +5.43] |

Receipt is balanced on every observable (`a3_covariate_balance.csv`, all gaps
under 1.4 pp), so the residual is not obviously spurious — which is why the
placebo tests matter. Both are reported **with their minimum detectable effects**,
because a null on an underpowered test is not evidence of absence: the
delivered-vs-undelivered comparison can only rule out effects larger than ~4 pp.
The honest conclusion is "at most +3.8 pp, plausibly zero", and the
recommendation is a holdout rather than a budget.

## On the Part B earnings figures

`fare_inr` is a deterministic function of distance (₹38 + ₹13.49/km, R² = 0.96)
and does not respond to the surge multiplier reported in `airport_hourly.csv`,
where night surge averages 1.96x. The two files disagree. All earnings-per-hour
figures are therefore surge-free and are a **lower bound**. If surge does reach
captain earnings, the fact that captains still avoid the night airport makes the
dead-heading diagnosis stronger, not weaker.

`airport_trips.csv` holds 51,740 completed trips against 81,756 fulfilled
terminal requests in `airport_hourly.csv`, so it is treated as a ~63% sample.
Population figures derived from it are scaled by 1.58x and labelled as estimates.

Engaged-hour calculations assume 22 km/h city driving and that a captain with no
follow-on fare waits the 20-minute window and then drives back the same distance.
Both are declared in `config.py`; the ranking of destinations is not sensitive to
either.

## Sizing: what the numbers are and are not

`a2_opportunity_sizing.csv` sizes each leak independently. Those leaks overlap —
a captain rejected on a blurred Insurance photo who never retried appears in two
of them — so **`a2_opportunity_sizing_dedup.csv` is the number to quote.** It
assigns every unapproved captain to exactly one primary reason and values them at
the observed approval rate of captains who cleared the document they are stuck on.
That per-captain weighting matters: a captain stuck on Insurance is worth about
4x one stuck on DL.

The populations and their onward conversion rates are measured. The recovery
rates are judgement, shown as low and high cases. These size the prize; they are
not a forecast.

## `explore/`

The ten scratch scripts from the initial investigation, kept for transparency
about how the findings were actually reached — including the hypotheses that went
nowhere, such as verification turnaround. They are not part of the pipeline,
print to stdout only, and expect to be run from inside `explore/`:

```bash
cd explore && ../.venv/Scripts/python 03_funnel.py
```

`run_all.py` does not depend on them.
